# Error Catalogue and Failure Behaviour

Two parts: the normative catalogue of every error the service can return, and the failure
scenarios that define what happens when a dependency is broken. Both are part of the contract.
An error code that appears in the API but not here, or here but not in the API, is a defect.

Two rules govern the whole design:

1. **Every failure is fast, typed, and distinguishable.** A client must be able to branch on the
   code, never on message text.
2. **Every failure is fail-closed and state-preserving.** A failure never permits an action, never
   partially applies a mutation, and never corrupts a balance (DR-037).

---

## 1. Response shape

Every non-2xx response uses one envelope. There is no second error format anywhere in the API.

```json
{
  "error": {
    "code": "quota_exceeded",
    "message": "balance 50 is less than requested 100",
    "request_id": "01JCQ7Z4K2M9XQ3F8V6T0B5NDE",
    "details": {
      "feature_key": "llm.tokens.output",
      "balance": 50,
      "requested": 100,
      "limit": 1000,
      "bonus": 0,
      "cycle_end": "2026-10-01T00:00:00+02:00"
    },
    "retry_after_ms": null,
    "documentation_url": "https://quotacore.dev/errors/quota_exceeded"
  }
}
```

| Field | Rule |
| --- | --- |
| `code` | Stable, lower snake case, never changes meaning. The only field a client should branch on |
| `message` | Human-readable, may improve between versions. Never parse it |
| `request_id` | Same value as the `X-Request-Id` response header and the `request_id` in the log line. Quote it in a bug report |
| `details` | Code-specific. Additive across versions; new keys may appear |
| `retry_after_ms` | Present only when retrying is the correct action |
| `documentation_url` | Stable per-code documentation path, resolvable to the hosted docs or the repo equivalent |

`request_id` is generated by the service on every request, honours an inbound `X-Request-Id` if it
is a valid ULID or UUID, and is never derived from user input in a way that allows injection into
logs.

## 2. Catalogue

`State changed` is the answer to the only question that matters during an incident: did the
caller get charged for the failure?

### 2.1 Client errors — 4xx

| Code | HTTP | When | State changed | Retryable | Client action |
| --- | --- | --- | --- | --- | --- |
| `validation_failed` | 400 | Malformed body, unknown field, bad amount, bad time zone, bad reset interval, window/cadence mismatch | no | no, fix input | Correct the request. `details.errors` names each offending field |
| `invalid_amount` | 400 | `amount` is negative | no | no | Use the endpoint for the direction you want. A sign is never a direction (DR-023) |
| `invalid_window` | 400 | `window` not valid for the feature's cadence, or unsupported for this release | no | no | Omit `window` for anchored cycles, or use a valid rolling window (v0.2) |
| `invalid_timezone` | 400 | Time zone is not a known IANA name | no | no | Use an IANA name such as `Europe/Berlin`. Abbreviations are rejected |
| `missing_idempotency_key` | 400 | `Idempotency-Key` absent on `consume` or `refund` | no | no | Send the header. Generate it in the SDK if available (DR-026) |
| `unauthorized` | 401 | No credential presented | no | no | Send `Authorization: Bearer <key>` |
| `api_key_invalid` | 401 | Key unknown, revoked, expired, or malformed | no | no | Rotate. There is no recovery path |
| `insufficient_scope` | 403 | Valid key, wrong scope | no | no | Issue a key with the required scope. `runtime` for the data plane, `admin` for control |
| `feature_not_in_plan` | 403 | No entitlement for the feature in the effective plan | no | no | Sell the feature, or grant an override — but an override cannot add a missing feature (DR-015) |
| `feature_archived` | 403 | Feature archived | no | no | Stop consuming. Balances are preserved, not zeroed (DR-016) |
| `tenant_suspended` | 403 | Tenant suspended | no | no | Contact the operator. Resuming restores the balance exactly (DR-032) |
| `tenant_not_found` | 404 | Unknown or soft-deleted tenant | no | no | Check provisioning. A recently provisioned tenant may not be visible yet (DR-031) |
| `feature_not_found` | 404 | Unknown feature key on the admin API | no | no | Check the key |
| `plan_not_found` | 404 | Unknown plan on the admin API | no | no | Check the plan identifier |
| `payload_too_large` | 413 | `metadata` above the size limit | no | no | Shrink `metadata`. It is a correlation aid, not a data store |
| `idempotency_key_reuse` | 409 | Key reused for a different operation | no | no, with a **new** key | Use a distinct key per logical operation (DR-028) |
| `plan_in_use` | 409 | Delete attempted while referenced | no | no | Archive instead |
| `feature_in_use` | 409 | Delete attempted while referenced | no | no | Archive instead |
| `feature_key_exists` | 409 | Duplicate feature key | no | no | Pick another key |
| `tenant_exists` | 409 | Duplicate `external_id` | no | no | Pick another identifier. Deliberately not idempotent, to surface the data error |
| `tenant_deleted` | 409 | Operation on a soft-deleted tenant | no | no | Soft deletion is terminal. Create a new tenant, or restore from a backup |
| `plan_key_exists` | 409 | Duplicate plan key | no | no | Pick another key |
| `refund_exceeds_grant` | 409 | Refund would break `balance <= limit + bonus` | no | no | Use an admin `grant` if the intent is a permanent increase (DR-019) |
| `grant_exceeds_ceiling` | 409 | Grant would break the ceiling | no | no | Raise the limit with an override first |
| `reset_not_supported` | 409 | Rollover attempted on a `never` entitlement | no | no | Grant explicitly. There is no cycle to roll (DR-008) |
| `feature_unit_immutable` | 409 | Unit change on an assigned feature | no | no | Create a new feature. Reinterpreting historical amounts is not allowed (INV-F2) |
| `resource_version_conflict` | 409 | Optimistic concurrency on a control-plane resource | no | after re-read | Re-read the resource and retry with the current version |
| `confirmation_required` | 409 | `apply-now` would affect more tenants than `QUOTACORE_PLAN_APPLY_CONFIRM_THRESHOLD`, so it applied nothing and returned a token | no | yes, by re-issuing **with** the token | Read `affected_tenants` and `earliest_cycle_end`, then re-issue with `confirmation_token`. Nothing was applied (DR-046) |
| `quota_exceeded` | 429 | `balance < amount` for `consume` | no | **at `cycle_end`** | Wait for the reset, or ask for a grant. `details.cycle_end` is authoritative |
| `rate_limited` | 429 | Service's own protective rate limit, per key | no | yes, with `Retry-After` | Back off. This is the *service* protecting itself, and is deliberately distinguishable from `quota_exceeded` (DR-040) |

### 2.2 Server errors — 5xx

| Code | HTTP | When | State changed | Retryable | Client action |
| --- | --- | --- | --- | --- | --- |
| `service_unavailable` | 503 | Data store unreachable, or the atomic script could not be evaluated | **no** | yes, with backoff and jitter | Fail open or closed **in your application**, deliberately (DR-037) |
| `control_plane_unavailable` | 503 | Postgres unreachable and the tenant is not in the snapshot | no | yes | Retry. Cached tenants are unaffected, which is why this code exists separately |
| `internal_error` | 500 | A defect | **must be no** | yes, with a new idempotency key only if the previous attempt is known not to have applied | Quote the `request_id`. A `500` on a mutation always means nothing was applied, because the mutation is atomic |
| `not_implemented` | 501 | A v0.2+ surface called on an MVP build | no | no | Upgrade, or use the MVP equivalent |

**The 500 guarantee.** A `500` on `consume` or `refund` always means the balance is unchanged.
The mutation is a single atomic script execution, so there is no state in which a deduction was
partially applied. This is a strong, testable guarantee and it is what makes a client-side retry
safe even after a `500`.

### 2.3 Error-code conventions

- Codes are permanent. A code may be retired only in a major version, and only if no client could
  reasonably depend on it.
- No code carries business meaning in its HTTP status alone. `429` means two different things
  (`quota_exceeded`, `rate_limited`) and clients must read `code`.
- No endpoint returns a bare `400` or a bare `500` without an envelope.
- Validation errors aggregate: a request with three bad fields returns one `validation_failed`
  naming all three, not three responses.

Each cell names complete routes. An earlier version of this table abbreviated them, with a bare verb
inheriting the first cell's path, and that was ambiguous in a way a reader could resolve two ways: a
bare `PATCH` on the features row is a collection `PATCH` or a `PATCH` of one feature, and only the
second has a `version` to conflict on. The contract check reads these cells, so a cell that can be
read two ways would have to be guessed at.

A cell that lists several routes states the codes those routes **can** return, not that each route
returns all of them. `POST /v1/admin/plans/{id}/apply` is the clearest case: it cannot return
`plan_key_exists`, but it shares a cell with the route that creates a plan. The union across a cell
is what the contract is checked against, and a code that is reachable on one route in the cell and
not another is the ordinary case, not an error.

Three constraints are expressed by what a route does **not** list, so they are stated here rather
than left to inference:

- `POST /v1/refund` never returns `quota_exceeded`. A refund cannot exceed a balance; the bound it
  can break is `balance <= limit + bonus`, which is `refund_exceeds_grant` (DR-019).
- `POST /v1/check` never returns `quota_exceeded` and never returns `idempotency_key_reuse`. A
  denial is `allowed: false` at `200`, and `check` mutates nothing, so there is no key to reuse
  (DR-024, [Q-07](assumptions-and-open-questions.md#2-open-questions)).
- `GET /v1/admin/status`, `GET /healthz`, `GET /readyz`, `GET /metrics`, `GET /openapi.json` and
  `GET /docs` return no error envelope, because they are the probe and operator surfaces rather
  than the API. `GET /v1/admin/status` still requires the `admin` scope (NFR-O5): it returns no
  envelope so that a dependency being down can be reported, which is the one thing it exists to do.

`tenant_deleted` and `plan_not_found` are in the matrix because the endpoints can reach those
states. A soft-deleted tenant is treated exactly as absent by every endpoint that takes an
identifier, which is why `tenant_not_found` remains the common response and `tenant_deleted`
appears only where a caller has already been authorised to see the tenant exists.

`payload_too_large` appears on every endpoint that accepts a request body, and on none that does
not, because the body is capped before it is parsed (NFR-T6, DR-016). That includes
`DELETE /v1/admin/tenants/{id}/overrides/{feature_key}`, whose only field is `apply_at`: the route
takes a body, so it is capped like every other one, and it is absent from every read route.

The rule is stated in terms of whether a route has a body rather than which HTTP method it uses,
because one route here is a `DELETE` that takes a body. `payload_too_large` on a `DELETE` is not a
mistake in the table, and a future route that takes a `DELETE` body will need it too.

## 4. Failure scenarios

The specific ways this system breaks, and the exact response. These are the scenarios that
separate a correct metering system from one that quietly loses money.

### FS-01 — Two concurrent requests for more than the balance remains
Two requests for `60` against a balance of `100`, arriving at the same instant.
**Behaviour:** the atomic script serialises them. One succeeds, the balance is `40`, the other
receives `429 quota_exceeded` with `balance: 40`. No overspend, no negative balance, no partial
deduction. Two events, not one.
**Why it matters:** this is the failure that a read-then-write implementation loses. It is the
reason the whole data plane is one script.

### FS-02 — A client's timeout fires after the server applied the deduction
The client sent `consume` with key `k`, the server applied it, and the response was lost.
**Behaviour:** the client retries with the same key `k`. The script finds the record, the
fingerprint matches, and it replays the stored response with `replayed: true`. The customer is
charged once.
**Why it matters:** without this, a network blip becomes a double charge. The API requires the
key precisely so that this scenario has a correct answer.

### FS-03 — A client retries with a *new* key after a timeout
**Behaviour:** a second deduction occurs. The system cannot detect this, and does not pretend to.
**Mitigation, in order:** the v0.5 SDKs reuse keys automatically; the API reference tells clients
to derive the key from their own durable operation identifier; the customer's database should hold
their operation record before calling. Documented plainly rather than engineered around, because
no server-side scheme can detect it.
**Why it matters:** stating the limit honestly is better than an implied guarantee that quietly
does not hold.

### FS-04 — A reused key with a different amount
**Behaviour:** `409 idempotency_key_reuse`, no state change, and the original record is preserved
so support can still retrieve the original outcome (INV-I2).

### FS-05 — The service was down across several cycle boundaries
A tenant's monthly cycle ended while the service was unavailable.
**Behaviour:** the next request computes the current window from the anchor and places the tenant
in it. One allowance, not three. Exactly one `cycle_rolled_over` event.
**Why it matters:** the naive "reset job missed" design grants multiple allowances to every
tenant after every outage. This is a silent revenue leak that nobody notices until the invoice.

### FS-06 — The request path and the reset worker race the same boundary
**Behaviour:** both compute the same target index. One applies the transition; the other is
rejected as stale and treats that as success. Exactly one event. The winner is irrelevant.

### FS-07 — The data store is unreachable
**Behaviour:** `503 service_unavailable` with `retry_after_ms`, within the latency budget. No
deduction, no partial write, no hang. The customer decides whether to fail open or closed.
**Explicitly not done:** a server-side fail-open switch. Converting an infrastructure outage into a
revenue outage is not a decision an infrastructure component should make unilaterally.

### FS-08 — Postgres is unreachable
**Behaviour:** tenants already in the snapshot cache continue to be enforced with full
correctness, because enforcement never reads Postgres (DR-039). An uncached tenant receives
`503 control_plane_unavailable`, which is deliberately a different code so the operator knows the
tenant simply needs to become cached, not that the service is down.
**Why it matters:** a control-plane outage must not take the enforcement path down. That
separation is the reason for two planes at all (ADR-0001).

### FS-09 — A configuration change and a request interleave
An operator raises a limit while `consume` requests are in flight.
**Behaviour:** the in-flight requests are evaluated against the configuration that was current
when they entered the script. The change becomes visible to subsequent requests at the next
cache-propagation bound, and to balances at the next cycle boundary. No request observes a
half-applied configuration, because a configuration read is a single atomic snapshot.

### FS-10 — An event cannot be written to the ledger
**Behaviour:** enforcement has already succeeded atomically in the data store. If the sink is
unavailable or saturated, the event is dropped, `quotacore_event_sink_dropped_total` increments,
and the request is **not** failed — a metered action that succeeded cannot be un-done by failing
the response, or the customer retries and is charged twice.
**Consequence, stated honestly:** the ledger has a gap, and a gap is visible in history and in
the metric. Reconstruction from the data store remains possible for a full-allowance-recovery case
(ADR-0016). This is a deliberate trade: at-least-once enforcement, best-effort history.

### FS-11 — A plan is changed mid-cycle
**Behaviour:** existing balances are untouched (DR-014). At each tenant's next boundary the new
limit applies. `apply-now` overrides this, is audited with a mandatory reason, and re-anchors every
assigned tenant. A per-tenant override changes one tenant immediately.
**Why it matters:** three different behaviours for three different intents. Getting this wrong
either breaks contracts or blocks urgent corrections, and the API makes the choice explicit rather
than defaulting silently.

### FS-12 — A customer retries an admin action after a timeout
**Behaviour:** the admin action carries an expected resource version. A retry with the stale
version returns `409 resource_version_conflict` and the operator re-reads. No blind double-apply,
no silent last-write-wins.

### FS-13 — The clock is wrong
**Behaviour:** the service trusts its own clock, as the sole time authority (DR-001). A clock
disagreement shifts a boundary, which shifts when an allowance resets. The `zone-data` version
and the current time are exposed in `GET /v1/admin/status` so the discrepancy is diagnosable.
**Required operational answer:** run NTP. Documented in the deployment guide and the README, not
left to discovery.

### FS-14 — Two days of spring-forward in a tenant's zone
**Behaviour:** the non-existent wall-clock boundary resolves forward to the first valid instant
(DR-007). The cycle is one hour short. This is correct behaviour, verified by the boundary test
table, and it is asserted rather than discovered in production.

### FS-15 — A refund arrives that would exceed the ceiling
**Behaviour:** `409 refund_exceeds_grant`. The balance is unchanged. The remedy for a legitimate
permanent increase is an admin `grant`, which raises the ceiling explicitly and is audited.
**Why it matters:** the ceiling is what makes it safe for the runtime scope to hold refund rights
at all. Without it, a compromised runtime key could inflate a customer's balance.

### FS-16 — A malicious caller probes with `amount: 0`
**Behaviour:** valid, allowed, records no event (DR-023). It cannot move a balance in either
direction, and it cannot be used to enumerate plans, because `feature_not_in_plan` is returned
identically whether or not the amount is zero.

### FS-17 — A malicious caller guesses a feature key
**Behaviour:** `403 feature_not_in_plan` for a key that does not exist on the tenant's plan, and
`404 feature_not_found` only on the admin API. On the data plane, existence is not disclosed,
because knowing which features exist is not a customer's entitlement. See
[security-model](../architecture/security-model.md).

### FS-18 — A runtime-scoped key attempts a control-plane call
**Behaviour:** `403 insufficient_scope`. Not `404`, because pretending the endpoint does not exist
only makes debugging harder for a legitimate integrator, and a runtime key holder already knows
the API surface.

### FS-19 — An `apply-now` is wider than the operator realised
**Behaviour:** `409 confirmation_required`, with `affected_tenants`, `earliest_cycle_end` and a
single-use `confirmation_token`. **No tenant is re-anchored.** The call is retried with the token
and then applies in full. Re-using the token is refused, and a token issued against an earlier
`resource_version` is refused.
**Why it matters:** `apply-now` re-anchors every assigned tenant's cycle at once. The failure this
prevents is not a customer-visible outage; it is an operator destroying a month of allowance
across a whole plan because the wrong `plan_id` was in the URL. The count is returned so the
operator can see the blast radius *before* committing to it, which is why the impact route exists.

### FS-20 — A tenant is soft-deleted while requests are in flight
**Behaviour:** three outcomes are permitted, and nothing else. A request that entered the protected
script before the delete committed may complete, and the deduction stands. A request that reads the
tenant after the delete commits is denied `404 tenant_not_found`, or `409 tenant_deleted` where the
caller is already authorised to see that the tenant exists. Deletion never unwinds a completed
deduction (DR-047).
**Why it matters:** the alternative — retroactively denying a request the server already
acknowledged — leaves the caller holding a deduction the ledger does not show, which is a worse
failure than the one it prevents. The remedy for a completed deduction is `POST /v1/refund`, not
the delete.

### FS-21 — The fast store is full
**Behaviour:** `503 service_unavailable`. The write is refused, not evicted, because the store runs
`maxmemory-policy noeviction` (DR-048). The balance is unchanged and the event count is unchanged,
so the request is safely retried once capacity is restored.
**Why it matters:** this is the deliberate trade of the second claim against the first. The store is
sized to hold the whole idempotency working set, so in normal operation this does not fire; when it
does, the failure is an availability event that is visible and alertable, in exchange for never
discarding a record that is the only thing preventing a second charge. Under the `allkeys-lru`
policy this specification previously specified, the same pressure would have silently evicted
idempotency records and produced a billing error instead, with no counter to show for it.

### FS-22 — The fast store is lost inside an idempotency window
**Behaviour:** the store is rebuilt from the ledger, and balances return exactly. Idempotency
records do **not** return, because they are not derivable from the ledger — the ledger records usage
and not keys. A client retrying a pre-loss request inside its window is therefore charged a second
time. Reconciliation detects the duplicate `event_id` and issues exactly one refund against that
key, restoring a single net charge (DR-049).
**Why it matters:** this is the hole that `noeviction` does not close, and it is the reason claim 2
is worded as "charged once, and a double charge caused by store loss is reversed" rather than
"charged once, unconditionally". A duplicate detected here is a correctness alarm that triggers a
remedy, not an informational counter that reports one.

## 5. Contract requirements this catalogue imposes

1. Every code in section 2 exists in `api/openapi.yaml` with the same status, and every code in
   the OpenAPI document exists here. Enforced by a contract test, so the two cannot drift.
2. No code is added without a documented client action. A code nobody knows how to handle is a
   worse outcome than a generic `500`.
3. `State changed` is part of the contract, not a comment. It is asserted for every code in the
   integration test suite: issue the failing request, then read the balance and the event count,
   and require them to be unchanged.
4. The `X-Request-Id` header is present on every response, successful or not, and matches
   `error.request_id`.
