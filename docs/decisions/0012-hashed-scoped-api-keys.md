# ADR-0012 — Hashed, scoped, rotatable API keys in PostgreSQL, with an environment bootstrap key

- **Status:** Accepted
- **Date:** 2026-09-27
- **Deciders:** project owner
- **Affects:** [SECURITY.md](../../SECURITY.md), [api-conventions](../architecture/api-conventions.md), [data-model](../architecture/data-model.md)

## Context

Quotacore has two privilege tiers that must not be confusable: the **runtime** scope, used by
the customer's application on the request path, and the **admin** scope, used by the customer's
backend to provision tenants and change plans. A leaked runtime key costs quota; a leaked admin
key is total compromise of the billing configuration.

The previous project history specified exactly two static bearer tokens in configuration, one
per tier.

## Options considered

**A — Two static tokens in environment variables (the previous proposal).**
- Pros: nothing to store, nothing to migrate, impossible to misconfigure scope, no database
  needed to boot the control plane.
- Cons: no revocation without a restart or redeploy; no record of which service is calling; no
  way to give a staging environment its own key; rotation of a leaked key is a coordinated
  event across every caller; and the two secrets live in whatever secret manager the customer
  already uses, which is correct, but a *named, scoped, revocable* credential is strictly more
  operable than an undifferentiated one.

**B — Hashed, scoped, rotatable keys stored in the control plane, seeded from the
  environment (chosen).**
- Keys are generated by the server, shown exactly once, stored only as a SHA-256 hash, and
  carry a name, a scope, creation and last-used timestamps, and a revocation state.
- A bootstrap key from the environment creates the first admin key on an empty database, so the
  first-run experience is unchanged.

**C — mTLS or short-lived JWTs.**
- Pros: strong identity, no long-lived secret at rest, per-request identity.
- Cons: the customer must run or integrate a token issuer, or present a client certificate.
  That is a large adoption tax on a sidecar that is supposed to drop into an existing
  application in an afternoon, and it makes the product impossible to try with `curl`.

## Decision

**Option B.**

- **Key format.** `qc_<scope>_<id>_<secret>`, for example `qc_rt_01HZY..._k3Jd9xQm`. The
  identifier segment is a UUIDv7 base32-encoded; the secret is 32 bytes from
  `crypto/rand`, base64url without padding. The visible prefix in the middle is what appears in
  logs and in the admin UI, so a human can identify a key without it being a secret.
- **Storage.** Only `sha256(secret)` is persisted, alongside the scope, name, status and
  timestamps. There is no path in the codebase that can read a key back. A database dump does not
  yield usable credentials.
- **Lookup.** The presented key is parsed, the identifier segment selects the row, and the
  stored hash is compared with `subtle.ConstantTimeCompare`. The comparison is constant-time so
  that response timing does not leak a prefix match.
- **Two scopes, no more.** `runtime` and `admin`. There is deliberately no per-feature or
  per-tenant scope in the MVP: the enforcement key belongs to the customer's own application,
  which is inside the trust boundary, and narrowing it to specific tenants would require the
  customer to re-issue keys on every onboarding. Documented as a deliberate simplification with
  a stated reason.
- **Revocation is immediate.** Revoking a key takes effect on the next request; the in-memory
  key cache carries a bounded TTL and a pub/sub invalidation on revoke, so revocation is not
  gated on cache expiry.
- **`last_used_at` is updated at most once per minute per key** and never on the request path's
  critical section. It is a diagnostic, not an audit trail; the audit log in
  [data-model](../architecture/data-model.md) is the audit trail.
- **Bootstrap.** If the `api_keys` table is empty and `QUOTACORE_BOOTSTRAP_ADMIN_KEY` is set,
  that key becomes the first admin key. If the table is non-empty, the variable is ignored and
  a warning is logged. The documentation instructs operators to remove it from the environment
  after first boot. Accepting an environment-provided key on an empty database is a deliberate
  trade: it is convenient, and the only way it is abusable is by someone who already has
  environment access, who could equally well read the database.
- **Transport.** Keys are sent as `Authorization: Bearer <key>`. Query-string keys are rejected
  outright, because they end up in access logs and browser history.

## Rationale

Two undifferentiated static tokens are adequate for a prototype and inadequate for anything a
customer runs in production, where the first question after a suspected leak is "which key, used
from where, revoke it now". Answering that requires named, scoped, revocable credentials with a
usage timestamp, and storing only a hash is what makes the "which key" answer safe to provide in
the first place.

Keyring-authenticated access is worth the cost for a service that sits in the revenue path: a
leaked admin key is not a bounded incident, so being able to revoke one key in one request
without a redeploy is worth a table and 200 lines.

Scope stays at two because the caller of the enforcement endpoint is the customer's own
codebase. Splitting it further would be security theatre that pays its cost in integration
friction.

## Consequences

**Positive**
- Immediate revocation of a leaked key, without a redeploy and without rotating every caller's
  configuration.
- Per-key attribution in logs and in `last_used_at`, so a leak has a blast radius.
- A stolen database backup does not yield usable credentials.
- The runtime and admin privileges are separable, so the key that rides on every request is not
  the key that can rewrite plans.
- First-run experience is unchanged: one environment variable, and the instance is usable.

**Negative**
- Authentication now depends on the control plane being reachable at boot. This is bounded: a
  warm key cache keeps enforcement working while Postgres is unavailable, and the key cache
  reload behaviour is specified in [runtime-data-plane](../architecture/request-lifecycle.md).
  A cold start with no reachable database and no cached keys fails readiness, which is correct.
- A SHA-256 hash of a 256-bit random secret is the right primitive here precisely because the
  secret is high-entropy. The storage approach is **not** safe for a human-chosen password and
  must never be reused for one. This is stated in the code as well as here.
- Bootstrap via environment variable means a stale bootstrap key in a deployment manifest is a
  latent risk, mitigated by ignoring it once keys exist and by the documentation.
- Two scopes means the service cannot express "a key that may only manage tenants in region
  eu". Not required in the MVP; noted as a future consideration.

## Revisit when

- A hosted, multi-tenant offering is built, at which point per-tenant key scoping becomes
  mandatory rather than optional.
- Customers require key expiry, per-tenant key binding, or mutual TLS.
