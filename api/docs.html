Quotacore

Version 0.1.0

Quotacore is a quota service. It holds a balance per tenant, per feature, and answers
whether a call is allowed before the call is made, or applies it after.

This document is the source of truth for the wire format. It is generated from
docs/architecture/api-conventions.md and docs/product/error-catalog.md, not from the
code, and the types and request validation in the service are generated from this file
(ADR-0010). A disagreement between this file and those documents is a defect in whichever
one was edited last.

Conventions that hold on every route in this document.

- Every response carries X-Request-Id, and the request_id in an error body equals it
  (NFR-S10). Quote it in a bug report.
- Every error body is the same envelope, and code is the only field to branch on. The HTTP
  status is a class hint; 429 in particular means two different things, which is
  quota_exceeded and rate_limited (DR-040).
- Idempotency-Key is required on POST /v1/consume and POST /v1/refund and on nothing
  else. There is no server-generated fallback, because a generated key silently defeats the
  purpose.
- Amounts are JSON integers, never floats. A float is 400 validation_failed naming the
  field.
- Timestamps are RFC 3339 with an explicit offset, always, including Z. A client never
  has to branch on whether the zone is UTC.
- cycle_start and cycle_end are null together, for a never entitlement. That is the
  documented shape, not an omission (DR-008, INV-C6).
- A request with an undeclared field is 400 validation_failed. Every object in this
  document sets additionalProperties: false, which is what makes a typo a clear error
  instead of a silently ignored key.
- Validation errors aggregate. Three bad fields produce one validation_failed naming all
  three, in details.errors.

Two guarantees worth reading before integrating.

A 500 on consume or refund always means the balance is unchanged. The mutation is a
single atomic script execution, so there is no state in which a deduction was partially
applied, and a client-side retry after a 500 is safe.

A retry with the same Idempotency-Key is charged once, within 24 hours of the first
application. A retry with a new key is a second operation and is charged twice. No
server-side scheme detects that (FS-03).

data-plane

The four routes a customer's application calls on the request path. These are the ones
with a latency budget, and the ones that open no database connection.

POST /v1/consume

Deduct an amount from the current cycle's balance

The call a customer's application makes instead of decrementing a counter itself.

Idempotency-Key is required. The same key replayed with the same
operation | tenant | feature | amount returns the original response byte for byte with
replayed: true, and the same key with a different fingerprint is
409 idempotency_key_reuse with no state change at all (DR-028, INV-I2).

The window is 24 hours from the first application. A key first seen after that is a new
operation, not a replay (DR-029). The window is fixed and is not configurable, because it
is a documented customer guarantee.

POST /v1/refund

Return an amount to the current cycle's balance

A refund is its own operation, not a negative consume. The direction is the endpoint and
never a sign (DR-023, ADR-0005), so a refund can never be confused with a malformed
amount.

Idempotency-Key is required, on the same 24-hour window as consume.

A refund never returns quota_exceeded. A refund cannot exceed a balance; the bound it
can break is balance <= limit + bonus, which is refund_exceeds_grant (DR-019). If the
intent is a permanent increase, use an admin grant instead.

POST /v1/check

Ask whether an amount would be allowed

Advisory. Returns 200 with allowed: false when the answer is no; a denial here is
not a 429 (DR-024). A 429 from this route means the service is rate-limiting
you, which is a different problem with a different remedy (DR-040).

No Idempotency-Key, because nothing is mutated, so a duplicate is harmless
(DR-024). This route never returns idempotency_key_reuse.

It is POST rather than GET because the question is in a body, and a GET with a body
is not portable. The verb is check and not quote because it reserves nothing.

The limitation is stated here as well as in the reference, because ignoring it looks like
a bug the first time a customer hits it: two requests can both pass check and one can
then be denied at consume. check reduces denials, it does not eliminate the race.

GET /v1/balance

Read the balances of a tenant

With feature_key, one entry. Without it, the tenant's full set, which is bounded by the
plan's entitlement count (NFR-T5), so the unbounded case does not exist. feature_key is
optional.

cycle_start and cycle_end are always present and are null together for a never
entitlement.

An unknown feature key on this route is 404 feature_not_found. This is the admin-plane
behaviour and it is the one documented exception to the data plane's non-disclosure rule:
the caller already knows a key it is asking about, and feature_not_in_plan would be
indistinguishable from an exhausted allowance, which is the distinction the caller most
needs (FS-17).

This re-anchors every tenant assigned to the plan, so it is guarded by blast radius
rather than by operator intent (DR-046).

no Idempotency-Key on this route, deliberately. The handshake is already exactly-once

have two opinions about whether it happened.

Type object

Set or replace a per-feature override. An override is a contract term and outranks the
plan: it survives later plan edits, because a plan is an offer and an override is what one
customer signed for (DR-011).

Clearing an override is DELETE /v1/admin/tenants/{id}/overrides/{feature_key}, not this
route, because the storage cannot represent an override that sets nothing.

`limit_value` and `interval` are both required and both nullable. UC-13 says "a limit,
a reset interval, or both", and a required-but-nullable field is how "this aspect is not
overridden" is stated without ambiguity. Requiring the key is deliberate: absence would
mean two things, that the aspect is inherited and that the operator forgot it, and a
quota system should not have a wire format with those two readings.

At least one of the two must be non-null, and this schema does not enforce that. It is
the one constraint in the contract that lives in the data store, as
tenant_overrides_not_empty, and a request that sends both null is
400 validation_failed. The reason is recorded here rather than papered over: expressing
it in JSON Schema needs an anyOf over object branches, and the generator
(ogen 1.24.0) cannot generate that, failing with "complex anyOf is not implemented yet".
Silently dropping the constraint from the document to make the generator happy would
leave a reader believing the wire format guarantees something it does not.
